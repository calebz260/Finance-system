# Database

PostgreSQL 17, accessed through Prisma 7 with the `pg` driver adapter.

**Phase 0 status:** the datasource, generated client, migration pipeline and seed pipeline are
wired and verified against a real database. The domain schema arrives in Phase 1. The
conventions below are fixed now, so every model added later follows them.

## Connecting

| Context                                  | Where the URL comes from                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------ |
| Application runtime                      | `DATABASE_URL` → validated config → `PrismaPg` adapter (`backend/src/lib/prisma.ts`) |
| Prisma CLI (`migrate`, `generate`, `db`) | `backend/prisma.config.ts`                                                           |
| Integration tests                        | `TEST_DATABASE_URL` (a separate database — **a test run truncates it**)              |

Prisma 7 no longer accepts `url` inside `datasource`, so there is no path by which a stray
schema file can point a migration at the wrong database.

The pool is configured explicitly in application code rather than through connection-string
parameters: bounded `max: 10`, 30-second idle recycling, 10-second connect timeout so a
request fails fast instead of queueing behind an unreachable database. The constraint that
matters in production is PostgreSQL's `max_connections`, shared by every instance —
`max × instances` must stay comfortably below it.

In development the client is cached on `globalThis`, so `tsx watch` reloading a module does
not open a new pool on every file save and exhaust connection slots.

## Conventions

Every model added from Phase 1 onward follows these. They are stated in
`backend/prisma/schema.prisma` as well, next to the code they govern.

### Money

```prisma
amount Decimal @db.Decimal(14, 2)
```

Never `Float`, never `Int` without a defined unit. Maximum representable amount is
999,999,999,999.99. All arithmetic happens server-side through the `Money` value object
(`shared/src/money.ts`), which rounds half-up at scale 2 and refuses to mix currencies.

### Timestamps

```prisma
createdAt DateTime @default(now()) @db.Timestamptz(3)
updatedAt DateTime @updatedAt      @db.Timestamptz(3)
```

Stored in UTC; converted to Africa/Kigali only in the presentation layer. The container and
CI service both run with `TZ=UTC`, and an integration test asserts the session time zone, so
a machine with a local time zone cannot quietly change behaviour.

### Keys and naming

- UUID primary keys, generated by the database.
- Snake_case tables and columns via `@@map` / `@map`; camelCase in TypeScript.
- Human-facing identifiers are separate from primary keys: `Student.studentId`
  (`STU-2026-00125`) and `Receipt.receiptNumber` (`RCP-2026-000001234`), each unique per
  school and validated against the shared patterns in `shared/src/identifiers.ts`.

### Tenant scoping

Every core table carries `schoolId`, with a foreign key to `schools` and an index on it.
Repository helpers apply the scope; queries never rely on a caller remembering to filter.
Unique constraints that are logically per-school are declared as composite uniques including
`schoolId` — for example `@@unique([schoolId, studentId])`, so two schools can each have a
`STU-2026-00001`.

### Optimistic locking

Rows that two staff members may edit at once — student financial accounts, payment records,
fee structures — carry:

```prisma
version Int @default(0)
```

An update matches on the expected version and increments it. Zero rows affected means someone
else won, and the request is rejected with `RECORD_MODIFIED` so the client reloads and retries
rather than silently overwriting.

### The financial ledger

From Phase 4, **a balance is never stored and never derived from business records.**
`financial_entries` is the authoritative ledger: charges, discounts, scholarship awards,
waivers, adjustments and — from Phase 5 — verified payments each post one row when they take
effect, and a balance is

```sql
SUM(amount) FILTER (WHERE entry_type = 'DEBIT')
  - SUM(amount) FILTER (WHERE entry_type = 'CREDIT')
```

over that table and nothing else. Amounts are always positive; direction lives in `entry_type`,
so no query has to reconstruct a sign convention.

The table is insert-only. An entry that turns out to be wrong is undone by posting an opposing
entry linked through `reversal_of_entry_id` — never by an UPDATE — so a reversal nets itself out
arithmetically and the account still records that both things happened. Partial unique indexes
permit exactly one opening entry per source record, which is what makes a double credit
impossible under a retry or two concurrent approvals rather than merely unlikely. See ADR-022.

There is deliberately **no balance column on any table**, and no `remainingAmount`, `totalPaid`
or `paidAt` on a charge: whether a charge is settled is derived, because a stored answer is one
a bug or a migration can set wrongly.

Adding payments cost this shape nothing, which was the point of it: `PAYMENT` became one more
value of `financial_entry_source`, a verified payment posts a CREDIT, a reversal or refund posts
the opposing DEBIT, and the formula above is untouched. `totalPaid` simply stopped being zero.

### Payments (Phase 5)

Five tables, and each of them exists because of a specific failure it prevents:

| Table                    | Why it is separate                                                                                                                                                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payments`               | What the school was asked to collect. `SUCCESSFUL` is the only status that has credited the ledger, and check constraints refuse one without a verifier, a terminal status without a completion timestamp, and cash with a provider key. |
| `payment_transactions`   | One attempt against a provider. Genuinely one-to-many: a payer whose first prompt timed out tries again, and the first attempt may still settle — the case that becomes a duplicate credit if attempts are collapsed into one row.       |
| `payment_status_history` | How a payment reached its current state. A status column cannot answer that: PENDING → REQUIRES_REVIEW → SUCCESSFUL looks identical to verified-first-time unless the middle step was written down.                                      |
| `payment_evidence`       | Proof behind a credit. Insert-only: replacing a slip supersedes the old row rather than overwriting it. The file lives outside the database and outside any web-servable path, keyed by an opaque server-generated `storage_key`.        |
| `payment_webhook_events` | Every inbound callback, verified or not, written **before** the callback is acted on. `(provider_key, event_id)` is unique, which is what makes webhook handling idempotent.                                                             |

The index that matters most is `financial_entries_one_opening_per_payment`: one partial unique
index on `(payment_id) WHERE source = 'PAYMENT' AND reversal_of_entry_id IS NULL`. Two
simultaneous callbacks, a provider retrying after a timeout, a bursar double-clicking Verify and
two concurrent finalisation transactions all end up attempting a second insert there, and all of
them lose. It is scoped to opening entries so the compensating DEBIT a reversal posts remains
possible.

### Reconciliation (Phase 5)

`bank_statement_imports` and `bank_statement_lines` hold what the bank said, and only that. A
line's date, narrative and amount are never edited to make a match work: a line that does not
fit a payment is a question about the payment, not a typo to correct.

- The import's `checksum` is unique per school, so the same export cannot be imported twice and
  double a month's work.
- `bank_statement_lines_one_line_per_payment`, a partial unique index on `matched_payment_id`,
  enforces one line per payment and one payment per line. Two lines claiming one payment would
  mean the bank paid the school twice and the school recorded it once.
- A check constraint refuses a `MATCHED` line with no payment, an unmatched line still holding
  one, an `IGNORED` line with no reason, and any attribution of a `MONEY_OUT` line — a bank
  charge credited to a family is money the school never received.
- Statement **files** are not stored: a statement is a transport for rows that are themselves
  stored. Proof of payment is the opposite and is stored. See [SECURITY.md](SECURITY.md).

### Deletion

Financial records and audit entries are never deleted. Soft deletion (`deletedAt`) is used
only where a record genuinely needs withdrawing from active use without destroying history,
and never as a substitute for a status field: a student who has left is a _status_, not a
deletion. A charge raised in error is **voided**, which keeps the row, records who and why, and
posts an opposing ledger entry.

### Transactions

Every multi-step financial write runs inside one interactive transaction — verifying a
payment, writing the ledger entry, allocating a receipt number and updating the balance either
all happen or none do. Rollback behaviour is asserted by an integration test rather than
assumed.

### Indexes

Added for the access patterns that actually exist: `schoolId` on every scoped table; foreign
keys; `(schoolId, studentId)`; payment lookups by status, date range and provider reference;
audit logs by entity and timestamp. Indexes are justified by a query, not added speculatively.

## Migrations

```bash
npm run db:migrate --workspace @sfs/backend          # create and apply (development)
npm run db:migrate:deploy --workspace @sfs/backend   # apply only (CI and production)
npm run db:migrate:status --workspace @sfs/backend   # what is pending
npm run db:reset --workspace @sfs/backend            # DESTRUCTIVE: drop, re-migrate, re-seed
```

Rules:

- Migrations are committed and forward-only. A mistake is corrected by a new migration, never
  by editing one that has already been applied anywhere.
- Never run `db:reset` against any database holding real data.
- A migration that changes existing financial data must be reviewed as carefully as
  application code, and must be reversible in effect even when not literally reversible.

## Seeding

```bash
npm run db:seed --workspace @sfs/backend
```

The seed refuses to run when `NODE_ENV=production`. It creates a school, roles and permissions,
a test account per role, academic years and terms, classes and programmes, students and
parents, fee categories, scholarship programmes and active fee structures — all fictional. It
must never contain real personal information.

**It raises no charges and records no payments**, and that is deliberate rather than
unfinished. The seed configures what a school charges; it does not bill a term or bank money.
Seeded charges would put obligations in the ledger that nobody authorised, and seeded payments
would put credits there that nobody verified — which is precisely the property Phases 4 and 5
are built to guarantee. A developer who wants either runs the charge run and the payment flow,
which is also the only way to see that they work.

## Local operations

```bash
npm run db:up      # start PostgreSQL 17 on localhost:5544
npm run db:down    # stop it
npm run db:studio --workspace @sfs/backend   # browse data
docker exec -it sfs-postgres psql -U sfs -d school_finance
```

The container publishes **5544** rather than 5432, because developer machines commonly already
run PostgreSQL on the default port. `infra/postgres/init/` creates the companion
`school_finance_test` database on first start.
